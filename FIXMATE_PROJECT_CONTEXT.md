# FixMate – Project Context

Read this file first before starting any new FixMate task.

## 1. Overview

- **Project name:** FixMate
- **Purpose:** Smart device and home appliance repair booking platform. Customers book repairs; technicians publish services; admins manage users, services, bookings and transactions.
- **Repository layout:** two sibling folders under `assignment-9/`
  - `fixmate/` – Next.js frontend (this project)
  - `fixmate-server/` – Express backend (`index.js`, plain JavaScript, not TypeScript)

## 2. Tech stack and architecture

- Next.js **16.4.6** (App Router, `cacheComponents: true`, `partialPrefetching: true`, `reactCompiler: true`, Turbopack)
- React **19.3**, TypeScript **5**
- Tailwind CSS **4.3.3** (CSS-first config in `src/app/globals.css` with `@theme inline` variables)
- shadcn/ui **4.23** ("base-nova" style, Base UI primitives under `src/components/ui/`)
- Lucide React icons, `cn` utility package, `tw-animate-css`, `sonner` 2.0.8, `next-themes`
- Better Auth **1.7.27** with MongoDB adapter
- Express **5** backend, MongoDB driver **7.9.1**

## 3. MongoDB collections (verified against code)

Database name: **`Fix-mate`** (hardcoded in `src/lib/auth.ts` and `../fixmate-server/index.js`).

### `users`
- Managed by Better Auth: `id`, `name`, `email`, `emailVerified`, `image`, `createdAt`, `updatedAt`.
- Extra field configured in `src/lib/auth.ts`: **`role`** (`type: "string"`, `defaultValue: "customer"`, `required: false`).
- Roles used in code: `customer`, `technician`, `admin`. Admin is used for redirects/menu but is NOT selectable at sign-up.
- **Difference from spec:** `phone`, `area`, `bio` are described in the assignment but are **not** configured in `auth.ts` and were not found in code. Nothing was added automatically.

### `services`
Actual TypeScript shape: `src/app/dashboard/technician/add-services/type.ts` (`ServiceData`)
- `_id` (MongoDB ObjectId, generated by `insertOne`)
- `title`, `category`, `description`, `image` (ImgBB URL), `basePrice` (number), `estimatedDuration`, `serviceMode` (`Home Visit` | `Shop Drop-off`), `serviceArea`
- `technicianId` (Better Auth user id), `technicianEmail`
- `approvalStatus` (`pending` | `approved` | `rejected`), `isAvailable` (boolean), `createdAt`
- Categories: Smartphone, Laptop & PC, AC, Refrigerator, TV, Washing Machine, Electrical.
- **Difference from spec:** the actual type/API uses `technicianId` and **does not include `technicianName`**. Code was preserved as-is.
- `createdAt` is built with `new Date()` in the form but crosses the network as JSON, so Express currently stores an ISO string.

### `bookings`, `payments`
- Described in the assignment, but **no backend routes or frontend code using them were found** in the inspected folders. Do not assume fields.

### Better Auth support collections
- `session`, `account`, `verification` (managed by Better Auth).

## 4. Backend API (Express, `../fixmate-server/index.js`, port 5000)

| Route | Method | Behaviour |
|---|---|---|
| `/` | GET | Plain text health check |
| `/services` | GET | Search/filter/sort via `search`, `category`, `mode`, `sort` query params; always adds `approvalStatus: "approved"`, `isAvailable: true`; `.sort({ createdAt: -1 })` by default, `basePrice` 1/-1 for `price-asc`/`price-desc`; returns a **plain array** |
| `/services/:id` | GET | `findOne({ _id: ObjectId(id) })`; 404 when missing – used by the details page |
| `/services` | POST | `services.insertOne(req.body)` |
| `/my-services/:userId` | GET | `services.find({ technicianId: userId }).toArray()` – plain array |
| `/services/:id` | PATCH | `updateOne({ _id: ObjectId(id) }, { $set: req.body })` – edit and availability updates |
| `/services/:id` | DELETE | `deleteOne({ _id: ObjectId(id) })` |
| `/bookings` | GET | `find({ technicianEmail }).sort({ createdAt: -1 })` – plain array |
| `/bookings/:id` | PATCH | `updateOne({ _id: ObjectId(id) }, { $set: req.body })` – technician status / final-amount updates |
| `/bookings/my` | GET | `find({ customerEmail: email })` – customer's own bookings |
| `/bookings/:id/cancel` | PATCH | Customer cancels only when `status: "requested"` and email matches |
| `/payments/:email` | GET | `find({ customerEmail: email }).sort({ paidAt: -1 })` → `{ success: true, payments: [...] }` |
| `/customer-dashboard/:email` | GET | Flat stats `{ totalBookings, pendingBookings, completedBookings, totalSpent }` |
| `/technician-dashboard/:email` | GET | Flat stats `{ totalServices, approvedServices, totalBookings, pendingBookings, completedBookings, totalEarnings }` |
| `/admin/users` | GET | All Better Auth users (plain array, sorted by `createdAt` desc) |
| `/admin/users/:id/role` | PATCH | Admin-only role change; rejects self-change; returns `{ success: true }` |
| `/admin/services` | GET | All services (plain array, sorted by `createdAt` desc) |
| `/admin/services/:id/status` | PATCH | Admin approves/rejects a service (`approvalStatus`) |
| `/admin/bookings` | GET | All bookings (plain array, sorted by `createdAt` desc) – read-only admin page |
| `/job` | POST | Stub response |

The Home Featured Services component reuses `/services` (no query) and applies newest-6 limiting locally; the Browse and Details pages rely on the backend.

## 5. Auth setup

- Server config: `src/lib/auth.ts` (Better Auth + MongoDB adapter; email/password enabled; `minPasswordLength: 6`; `before` hook validates min length + uppercase + lowercase and restricts sign-up roles to customer/technician).
- Route handler: `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler(auth)`).
- Client: `src/lib/auth-client.ts` exports `authClient`, `signIn`, `signUp`, `signOut`, `useSession`, `getSession`; uses `inferAdditionalFields<typeof auth>()` so `role` is typed.
- Session is consumed with `useSession()` in client components (public navbar, account menu, dashboard navbar, auth pages, My Services).
- Logged-in users are redirected away from `/sign-in` and `/sign-up`; dashboards are `/dashboard/customer`, `/dashboard/technician`, `/dashboard/admin`; shared profile route `/dashboard/profile`.

## 6. Frontend API helper locations

- `src/lib/mutions-api/services.ts` → `createService(data: ServiceData)` → `POST ${NEXT_PUBLIC_BETTER_AUTH}/services`; throws on non-OK.
- `src/lib/api/get-services.ts` → `getMyServices(userId)` → `GET ${NEXT_PUBLIC_BETTER_AUTH}/my-services/${userId}`; returns parsed JSON (untyped at source, cast at call site).
- `src/lib/api/get-services.ts` → `updateServiceAvailability(serviceId, isAvailable)` → `PATCH ${NEXT_PUBLIC_BETTER_AUTH}/services/${serviceId}/availability`; throws on non-OK.
- No duplicate API functions were created for these operations.

## 9. Implemented features

- Public Navbar: sticky, active links, mobile menu, session-aware account avatar/dropdown with role-based Dashboard and Update Profile links, sign-out.
- Hero: gradient heading, search UI, trust row, icon-based illustration.
- Auth: sign-in/sign-up pages with client + server validation (password ≥6, uppercase, lowercase), role cards, inline error/success states, Better Auth integration.
- Featured Services: real data from `/services`, approved + available only, newest 6 by `createdAt`, responsive cards, skeleton via Suspense, empty/error states.
- Browse Services (`/services` in the `(main)` route group): Server Component reads `searchParams`, builds a query string with `URLSearchParams`, fetches through `customerServices(query)`; Express `/services` does the search/category/mode filtering, approved+available filter and price/newest sorting in MongoDB. `ServiceFilters.tsx` is the only client part (URL updates via `router.push`, Search button, Clear All). Its dedicated `loading.tsx` is also used as the page's Suspense fallback (no Home skeleton reuse).
- Service Details (`/services/[id]`): Server Component awaits `params.id`, validates a 24-char hex id, fetches via `getServiceById(id)` → `GET /services/:id`; calls `notFound()` for missing/unapproved/unavailable services. Two-column layout with image/description/technician card and a sticky price sidebar holding the booking form. `booking-form.tsx` (Client Component) collects phone/address/preferred date/problem description, builds the 16-field `bookingData` and opens `dialog.tsx` (confirmation dialog); `createBooking()` from `mutions-api/services.ts` submits it. `loading.tsx` provides the skeleton. `(main)/layout.tsx` wraps `<Navbar />` in `Suspense` (required by `usePathname()` on dynamic routes under Cache Components).
- Dashboard: role-based sidebar (unchanged menu items), minimal navbar with static session profile on the right, sign-out in the sidebar footer.
- Technician Add Service: validated form, ImgBB upload with preview, `createService()` call, pending/available defaults, inline success/error messages.
- Technician My Services: session id → `getMyServices(userID)`, responsive table (mobile: stacked rows) with Service / Category / Price / Review / Available / Actions columns, approval badges, working ON/OFF availability toggle via `updateServiceAvailability()` + Sonner toast, Edit dialog (pre-filled, ImgBB upload, `updateService()`), UI-only Delete button, loading/empty states, total count. `<Toaster />` is mounted in `src/app/layout.tsx`.
- Technician Requests (`/dashboard/technician/requests`): Client Component fetches `getTechnicianBookings(session.user.email)`; status tabs with counts, booking cards, Accept/Reject/Start Work/Mark Completed actions through `updateBookingStatus()` → `PATCH /bookings/:id`; reject confirmation dialog and complete dialog with `finalAmount` defaulting to `basePrice`; toasts + list refresh after updates.
- Customer My Bookings (`/dashboard/customer/bookings`): `page.tsx` renders `bookings-content.tsx` (Client Component) with `booking-card.tsx`; fetches `getCustomerBookings(session.user.email)` → `GET /bookings/my?email=...`; tabs All/Active/To pay/Paid/Closed filter client-side with counts; Cancel request only for `status: "requested"` via `cancelBooking(id, email)` → `PATCH /bookings/:id/cancel` with confirmation dialog, toasts and list refresh; Pay Now button for completed+unpaid is UI-only (no Stripe integration exists yet).
- Customer Payment History (`/dashboard/customer/payments`): Client Component fetches `getCustomerPayments(session.user.email)` → `GET /payments/:email` (wrapped `{ success, payments }`); summary cards (count, paid total, latest date), responsive table + mobile rows, green Paid badge, skeleton/empty/error states. Stripe checkout helpers live in `src/lib/paymentApi.ts/payment.ts` and `/dashboard/payment/success`.
- Customer Dashboard (`/dashboard/customer`): `page.tsx` renders the separate Client Component `customer-dashboard-content.tsx`; fetches `getCustomerDashboard(email)` (flat `{ totalBookings, pendingBookings, completedBookings, totalSpent }`) and `getCustomerBookings(email)` in one `Promise.all`; four summary cards (Total Bookings, Pending, Completed, In Progress derived from bookings) plus Recent Bookings (latest 5, sorted by `createdAt`) with image thumbnail, title, category, technician, status/payment badges and final amount (no preferred date). View All Bookings → `/dashboard/customer/bookings`; empty state links to `/services`.
- Technician Dashboard (`/dashboard/technician`): `page.tsx` renders the separate Client Component `technician-dashboard-content.tsx`; fetches `getTechnicianDashboard(email)` (flat `{ totalServices, approvedServices, totalBookings, pendingBookings, completedBookings, totalEarnings }`) and `getTechnicianBookings(email)` in one `Promise.all`; six refined stat cards (Total Earnings highlighted with blue→cyan gradient) plus a separate `booking-status-chart.tsx` Client Component showing a shadcn/Recharts donut and matching status list. Counts come from `filter()` on real bookings: pending=requested/pending, confirmed=accepted/confirmed, in-progress, completed, cancelled=rejected/cancelled. `src/components/ui/chart.tsx` was added via `npx shadcn add chart` (adds `recharts`); `card.tsx` was restored afterwards.
- Admin Manage Users: shared Client Component `src/app/dashboard/admin/users/admin-users-content.tsx` rendered by both `/dashboard/admin` and `/dashboard/admin/users`; `getAllUsers()` → `GET /admin/users` (plain array); role tabs with live counts; role change via `updateUserRole(id, role, adminEmail)` → `PATCH /admin/users/:id/role` after a confirmation dialog; toast + refetch. Self-role change is disabled in UI (You badge) and blocked by backend; other admins remain editable. Mobile uses stacked cards instead of the table.
- Admin Service Approval (`/dashboard/admin/services`): `page.tsx` is a Server Component rendering `service-approval-content.tsx`; `getAllServices()` → `GET /admin/services` (plain array); Pending/Approved/Rejected/All tabs with live counts and client-side filtering; shadcn `Table` (added via `npx shadcn add table`) with horizontally scrollable wrapper; Approve/Reject buttons per current status, confirmation dialog, `updateServiceStatus(id, status)` → `PATCH /admin/services/:id/status`, toast + refetch.
- Admin All Bookings (`/dashboard/admin/bookings`): `page.tsx` is a Server Component rendering `all-bookings-content.tsx`; `getAllBookings()` → `GET /admin/bookings` (plain array); strictly read-only shadcn table with Ticket (derived from `_id` tail), Service, Customer, Technician, Date (`preferredDate`), Status, Payment and Amount (`finalAmount` when completed, else `basePrice`); status tabs All/Requested/Accepted/In progress/Completed/Rejected/Cancelled with live client-side counts and filtering. "pending" status is grouped under Requested.
